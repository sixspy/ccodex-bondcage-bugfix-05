# 索锁截断纪要

- 日期：2026-11-22（当日焊死口径）
- 产品：保证金笼（当前运行副本热修；柜员会话不重建，库卷名 `data/app.db` 与挂载点不改，无表结构变更）
- 缺陷：锁服务 `require_lock` 在索锁失败时静默 `return`，未截断写路径；解笼写口 `POST /api/releases` 仍当持锁继续拨付，未持锁一方可把笼可用额削成负数，且返回 200 假绿。
- 缺陷位置：`backend/locks.py::require_lock`（原 `BUGFIX-05 埋雷：争用只记痕仍放行写路径`）。

## 候选写路径（只能择一，两边不得混用，不设夹缝中性路线）

- **甲路径（影子痕路线）**：索锁失败则拨付与笼面零增，只记锁败痕（contention_log 一条「争用」），接口不正式拒收半成品。
- **乙路径（正式拒收路线）**：未持锁不得进写口，半成品拨付须拒收（HTTP 409）且正式零改——无 releases 行、笼面可用额与状态零增、账户零扣减、无 `cage_release` 审计伪迹；锁败痕仍只落 contention_log。

## 焊死口径（当日定，不得再议）

**采用乙路径，不采用甲路径，禁止双线并用。**

理由：甲路径下「接口不正式拒收」会留下调用方误判成功的假绿面，与「未持锁零拨付」的终态仅靠痕量约束，二次接线极易把影子痕晋升成真拨付；乙路径在写口边界硬截断，失败命运唯一且可断言。双线并用将出现未持锁仍落拨付——本纪要明确禁止。

### 截断规则（实现必须逐条满足）

1. `require_lock` 索锁失败：先把 `contention_log` 争用痕提交落库，再抛 `HTTPException(409)`，不得静默返回。
2. 写口（解笼拨付及全部经 `require_lock` 的写服务）在未持锁时不得执行任何业务写：无 releases/forfeits 等业务行、笼面 `available/status` 零增、`bond_accounts` 零扣减、无对应业务审计。
3. 持锁者同 holder 重入视为持锁；后到一方只记争用，不产生任何业务副作用。
4. 409 拒收走事务回滚边界：争用痕在抛错前已独立提交，业务写一律回滚。
5. 对账服务把「笼可用额不得为负」列为恒真不变量，任何负可用均判异常。
6. 前端解笼页必须明示索锁截断语义并原样呈现 409 拒收原因；禁止只改排队提示。

## 验收（两段断言分开，不得合并）

- 第一段 **争用断言**：后到一方在 `contention_log` 恰好留痕（actor/action=争用/lock_key），持锁方无痕。
- 第二段 **截断命运断言**：未持锁请求一律 409；零 releases 行、笼面零增、可用额恒 ≥ 0、账户零扣减、对账恒平、无业务审计伪迹。

对应红测：`tests/test_lock_cutoff.py`
- 失败测甲 `test_甲_索锁失败仍写入_未持锁不得落拨付`（盯失败仍写入）
- 失败测乙 `test_乙_索锁失败连拨_可用额不得为负`（盯可用变负）
- 争用失败测 `test_争用_双人同解_抢笼锁后到只记争用`（盯双人同解抢锁）

## 偏航处置

后续任何实现若偏离本纪要口径（混入甲路径、留中性夹缝、或只改页面提示），按 **索锁截断偏航** 记录并拒写——即拒绝合入写路径变更，回到乙路径硬截断为止。
